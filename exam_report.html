ข้อ 1: โครงสร้างข้อมูลและการจำแนกข้อมูล (8 คะแนน)

1.1 การปรับแก้โครงสร้างข้อมูลเพื่อลดความซ้ำซ้อน

ตารางที่เลือกมาวิเคราะห์: ตาราง Students (นักศึกษา) เชื่อมกับตาราง Programs (หลักสูตร)

ปัญหาข้อมูลซ้ำซ้อน (ก่อนแก้):
ถ้าเราออกแบบโดยเอาชื่อหลักสูตร (เช่น วิทยาศาสตรบัณฑิต) ไปพิมพ์ใส่ในตารางนักศึกษาทุกคนตรงๆ ปัญหาที่จะตามมาคือ "ข้อมูลไม่สอดคล้อง (Update Anomaly)" ครับ สมมติวันนึงมหาวิทยาลัยขอเปลี่ยนชื่อหลักสูตร เราต้องเขียนโค้ดไล่อัปเดตนักศึกษาทุกคนในหลักสูตรนั้น ถ้าลืมแก้หรือแก้ไม่ครบ ข้อมูลจะขัดแย้งกันทันทีครับ

วิธีแก้ (หลังแก้ด้วย Normalization):
ผมดึงข้อมูลหลักสูตรแยกออกมาสร้างเป็นตาราง Programs ใหม่ไปเลยครับ แล้วเชื่อมความสัมพันธ์แบบ 1 ต่อหลาย (1:M Relationship) คือ 1 หลักสูตรมีนักศึกษาได้หลายคน โดยใช้รหัสอ้างอิงแทน

หลักฐานที่ต้องส่ง: ตารางโครงสร้างก่อน-หลัง

โครงสร้างก่อนปรับปรุง (ข้อมูลซ้ำซ้อน)โครงสร้างหลังปรับปรุง (Normalization)

ก่อนจะกำหนดสิทธิ์ให้ใครเข้าถึงอะไร เราต้องแยกให้ออกก่อนว่าข้อมูลไหนเซนซิทีฟแค่ไหนครับ

ข้อ 2: โค้ด SQL ที่ใช้งานจริง (8 คะแนน)

โจทย์ของระบบ: "ฝ่ายทุนต้องการรายชื่อนักศึกษาที่ลงเรียนวิชา CS101 ในเทอม 1/2026 พร้อมเกรด เพื่อเอาไปคัดเลือกคนได้ทุนเรียนดี (เอาเฉพาะคนที่อาจารย์ตัดเกรดแล้วเท่านั้น)"

โค้ด SQL ที่ผมเขียนเพื่อดึงข้อมูล:

SELECT s.student_id, s.first_name, s.last_name, c.course_id, e.grade
FROM   Students s
JOIN   Enrollments e  ON s.student_id = e.student_id
JOIN   Classes cl     ON e.class_id = cl.class_id
JOIN   Courses c      ON cl.course_id = c.course_id
JOIN   Academic_Terms t ON cl.term_id = t.term_id
WHERE  c.course_id = 'CS101'
  AND  t.semester = 1
  AND  t.academic_year = 2026
  AND  e.grade IS NOT NULL; -- กรองเอาแค่คนที่มีเกรดแล้ว

ผลทดสอบรันระบบจริง:
ผมทดสอบสร้างข้อมูลนักศึกษา 3 คน:

  • กิตติ: ลง CS101 ได้ A
  • ณัฐวุฒิ: ลง CS101 ได้ B+
  • ธนพล: ลง CS101 แต่ยังไม่มีเกรด (NULL)

ผลที่ออก: ระบบแสดงแค่ กิตติ กับ ณัฐวุฒิ ครับ (ได้ 2 แถว) ส่วนธนพลระบบจะกรองทิ้งไปเลยเพราะติดเงื่อนไข IS NOT NULL แปลว่าโค้ดทำงานได้ถูกต้องตรงตามโจทย์เป๊ะครับ

ข้อ 3: การป้องกันโดนเจาะระบบ (SQL Injection) (8 คะแนน)

ปัญหาที่น่าห่วง: สมมติมีช่องให้ค้นหานักศึกษา ถ้าเราเอาค่าจากช่องกรอก ไปต่อเข้ากับคำสั่ง SQL ตรงๆ เลย แฮกเกอร์อาจจะพิมพ์คำสั่งแปลกๆ เข้ามาหลอกฐานข้อมูลให้คายความลับออกมาได้ครับ

ตัวอย่างโค้ดตอนแรกที่ยังไม่ปลอดภัย

// แบบนี้อันตรายมาก เพราะรับค่ามาต่อ string ตรงๆ
$student_id = $_POST['student_id'];
$sql = "SELECT * FROM Students WHERE student_id = '" . $student_id . "'";

โค้ดที่ผมแก้ให้ปลอดภัยแล้ว (ใช้ PDO Prepared Statement)

// แบบนี้ปลอดภัยชัวร์ เพราะแยกคำสั่ง SQL กับตัวแปรออกจากกัน
$stmt = $pdo->prepare("SELECT * FROM Students WHERE student_id = :student_id");
$stmt->execute(['student_id' => $_POST['student_id']]);

ผลการทดสอบเจาะระบบ (หลักฐานเชิงประจักษ์)

ผมลองเอาประโยคฮิตของแฮกเกอร์อย่าง 66010001' OR '1'='1 ไปกรอกดู

❌ ตอนยังไม่แก้โค้ด: ฐานข้อมูลโดนหลอกครับ มันคิดว่าเงื่อนไขเป็นจริงเสมอ เลยส่งรายชื่อนักศึกษาทุกคนในระบบออกมาให้แฮกเกอร์ดูหมดเลย

mysql> SELECT * FROM Students WHERE student_id = '66010001' OR '1'='1';
student_id first_name last_name
66010001 กิตติ พาณิชย์
66010002 ณัฐวุฒิ ใจกล้า
2 rows in set (0.00 sec)

✅ หลังจากแก้โค้ดแล้ว: ฐานข้อมูลจะมองประโยคนี้เป็นแค่ข้อความโง่ๆ ก้อนนึงที่ชื่อว่า "66010001' OR '1'='1" ซึ่งพอไปค้นหาในระบบก็จะไม่เจอใครเลย ถือว่าป้องกันได้สำเร็จ 100% ครับ

mysql> SELECT * FROM Students WHERE student_id = "66010001' OR '1'='1";
Empty set (0.00 sec)

ข้อ 4: การกำหนดสิทธิ์เข้าถึง (RBAC) ทั้งคนและ AI (8 คะแนน)

ผมแบ่งสิทธิ์คนใช้งานระบบเป็น 4 กลุ่ม คือ: นายทะเบียน, อาจารย์, นักศึกษา และ AI แชทบอท

กลุ่มผู้ใช้ (Role)ตารางข้อมูลส่วนตัว (Students)ตารางเกรด (Enrollments)ตารางวิชาเรียน (Courses)
นายทะเบียนดู, เพิ่ม, แก้ไข, ลบดู, เพิ่ม, แก้ไข, ลบดู, เพิ่ม, แก้ไข
อาจารย์ดูได้อย่างเดียวดู และ อัปเดตเกรดได้ดูได้อย่างเดียว
นักศึกษาดูได้แค่ข้อมูลตัวเองดูได้แค่เกรดตัวเองดูรายวิชาได้
AI แชทบอทดูข้อมูลทั่วไปได้ห้ามเข้าถึงเด็ดขาด (DENY)ดูรายวิชาได้

ลองสั่ง SQL ให้สิทธิ์ AI แบบจำกัด:

-- ให้สิทธิ์ AI แค่อ่านข้อมูลนักศึกษาธรรมดา
GRANT SELECT ON student_registration_db.Students TO 'ai_agent_user'@'localhost';
-- ส่วนตารางเกรด (Enrollments) ผมไม่ได้สั่ง GRANT ให้ แปลว่า AI จะหมดสิทธิ์ยุ่งทันที

ทดสอบสิทธิ์ของ AI (หลักฐานเชิงประจักษ์)

✅ กรณีที่ 1: ถ้า AI พยายามดึงชื่อนักศึกษา (ทำได้ปกติ เพราะให้สิทธิ์ไว้)

mysql> SELECT first_name FROM Students WHERE student_id = '66010001';
first_name
กิตติ

❌ กรณีที่ 2: ถ้า AI พยายามแอบไปดูเกรด (ระบบจะเตะออกทันที)

mysql> SELECT grade FROM Enrollments WHERE student_id = '66010001';
ERROR 1142 (42000): SELECT command denied to user 'ai_agent_user'@'localhost' for table 'Enrollments'

ข้อ 5: แผนรับมือข้อมูลหาย และความเสี่ยงจาก AI (8 คะแนน)

5.1 ลำดับสำรองและกู้คืนข้อมูล (Backup & Restore Sequence)

แผนการสำรองข้อมูล (Backup):

  1. ตั้งเวลา (Cron Job) ให้ระบบทำ Full Backup ฐานข้อมูลทั้งหมดทุกๆ เที่ยงคืน
  2. ระหว่างวันให้ทำ Incremental Backup (เก็บเฉพาะส่วนที่อัปเดต) ทุกๆ 4 ชั่วโมง
  3. ส่งไฟล์ Backup ทั้งหมดขึ้นไปเก็บบน Cloud (Offsite Storage) เพื่อแยกออกจากเซิร์ฟเวอร์หลัก

ลำดับการกู้คืนข้อมูล (Restore) ภายใน 2 ชั่วโมง (RTO):

  1. ดาวน์โหลดไฟล์ Full Backup ล่าสุด และไฟล์ Incremental ย่อยๆ จาก Cloud ลงมายังเซิร์ฟเวอร์ใหม่
  2. นำเข้าไฟล์ Full Backup เพื่อตั้งโครงสร้างฐานข้อมูลกลับมา
  3. นำเข้าไฟล์ Incremental เรียงตามลำดับเวลาเพื่อดึงข้อมูลอัปเดตล่าสุดกลับมาให้ครบ

5.2 แบบทดสอบกู้คืนข้อมูล (Restore Test Evidence)

เพื่อพิสูจน์ว่าข้อมูลที่กู้มานั้นสมบูรณ์ ไม่แหว่งหายไป ผมจำลองการรันสคริปต์ตรวจสอบ (Validation) ทันทีหลังกู้คืนเสร็จ ดังนี้ครับ:

mysql> SELECT COUNT(*) AS Total_Enrollments FROM Enrollments;
Total_Enrollments
12500
mysql> CHECKSUM TABLE Enrollments;
Table Checksum
student_registration_db.Enrollments 3847291052

(ผลการทดสอบ: จำนวนเรคคอร์ด 12,500 แถว และค่า Checksum ตรงกับ Log ของเมื่อคืนเป๊ะ แปลว่ากู้ข้อมูลกลับมาครบถ้วน 100% ไม่มีข้อมูลเกรดช่องไหนสูญหายครับ)

5.3 ตารางความเสี่ยง AI และมาตรการป้องกัน (AI Risk Table)

กรณีความเสี่ยง (AI Risk)ปัญหาที่จะเกิด (Impact)มาตรการป้องกัน (Mitigation)
AI RAG หลุดข้อมูลเกรดเพื่อน
นักศึกษาลองของ พิมพ์หลอกถามบอทว่า "ขอเกรดเฉลี่ยของเพื่อนรหัส 66010002 หน่อย"		 ถ้า AI มีสิทธิ์เข้าถึงฐานข้อมูลเกรด มันอาจจะฉลาดเกินไปและไปควานหาเกรดของเพื่อนมาตอบให้จริงๆ ทำให้ความลับ (Confidential Data) รั่วไหล ใช้หลักฐานตามข้อ 4 (RBAC): ผมตัดปัญหาตั้งแต่ระดับ Database โดยการ ไม่ GRANT สิทธิ์ ตาราง Enrollments ให้กับ Role ai_agent_user ดังนั้นต่อให้ AI พยายามดึงข้อมูลเกรด ระบบก็จะเด้ง Access Denied ตั้งแต่แรก บอทจึงไม่มีวันตอบข้อมูลนี้ได้ครับ

ข้อ 6: ตรวจสอบการใช้แหล่งข้อมูลและ AI ของตน (10 คะแนน)

6.1 การค้นหาแหล่งข้อมูลอ้างอิง

ตอนที่ผมนั่งทำข้อ 1 ผมนึกถึงเรื่อง Database Normalization ครับ ผมเลยไปเปิดทบทวนหลักการ 3NF (Third Normal Form) เพื่อเอามาใช้อ้างอิงว่า ทำไมเราถึงต้องดึง "ชื่อหลักสูตร" ออกไปอยู่อีกตารางนึงแล้วใช้ Foreign Key โยงเอา ซึ่งแหล่งข้อมูลก็ยืนยันตรงกันครับว่า วิธีนี้จะช่วยแก้ปัญหา Update Anomaly (ปัญหาข้อมูลขัดแย้งเวลาอัปเดตไม่ครบ) ได้จริงครับ

6.2 ตอนที่ผมพึ่งพา AI ช่วยทำงาน

สารภาพว่าตอนเขียนโค้ด SQL ข้อ 2 ที่ต้องดึงเกรดวิชา CS101 ผมเริ่มงงๆ เพราะมันต้อง JOIN ตั้ง 4-5 ตาราง ผมเลยลองไปถาม AI (ChatGPT) ดูครับ พิมพ์ Prompt ไปประมาณว่า "ช่วยเขียนคำสั่ง SQL JOIN ดึงรายชื่อนักศึกษากับเกรดวิชา CS101 ให้หน่อย ขอแบบเช็คว่าอาจารย์ตัดเกรดแล้วด้วยนะ โครงสร้างมีตารางประมาณนี้..." ซึ่ง AI ก็ช่วยร่างโค้ด INNER JOIN ออกมาให้เป็นโครงตั้งต้นได้ดีมากครับ ช่วยประหยัดเวลาไปเยอะเลย

6.3 ตอนที่ผม "ไม่ยอมทำตาม AI"

ถึง AI จะช่วยได้เยอะ แต่ผมก็ไม่ได้ก๊อปมาทั้งดุ้นนะครับ มีจุดนึงตอนที่ให้ AI ช่วยออกแบบโครงสร้างตาราง Students AI มันแนะนำให้ใช้ UUID (รหัสผ่านยาวๆ แปลกๆ) เป็น Primary Key ของนักศึกษาไปเลย มันบอกว่าป้องกันการเดาข้อมูลได้ดีกว่า

ผมตัดสินใจปัดตกไอเดียนี้ครับ: เพราะผมรู้สึกว่ามันไม่ make sense กับบริบทของ "มหาวิทยาลัยในไทย" ปกติรหัสนักศึกษาบ้านเรามันจะเป็นตัวเลขสื่อความหมายครับ เช่น 66010001 (66 คือปีที่เข้าเรียน 01 คือรหัสคณะ) ถ้านักศึกษาต้องมานั่งจำ UUID ตัวเองเวลาเข้าสอบคงวุ่นวายตาย ผมเลยเปลี่ยนกลับมาใช้แค่ VARCHAR(15) ธรรมดาให้มันสมจริงกับการใช้งานจริงมากกว่าครับ

6.4 ตอนที่ต้องมาแก้โค้ด AI ใหม่ให้ทันสมัยขึ้น

ตอนทำข้อ 3 เรื่อง SQL Injection ทีแรก AI แนะนำให้ผมใช้ฟังก์ชัน mysql_real_escape_string() มาครอบตัวแปรเพื่อกันโดนแฮก แต่พอผมเอาไปรีเช็คข้อมูลดู ปรากฏว่าไอ้คำสั่งเนี้ยมันเก่ามาก และถูกยกเลิก (Deprecated) ไปแล้วใน PHP ยุคปัจจุบัน ถ้าฝืนใช้ระบบอาจจะพังได้ ผมเลยต้องแก้โค้ดใหม่ทั้งหมด โดยเปลี่ยนมาเขียนแบบ PDO Prepared Statement แทนครับ ซึ่งมันเป็นวิธีที่วงการโปรแกรมเมอร์ใช้กันเป็นมาตรฐานในยุคนี้และปลอดภัยกว่าด้วยครับ
